# 개발팀 직무교육자료 (Development Department Training Materials)

> 대상: 개발팀 신입/전배 개발자, 타 부서에서 개발팀으로 전입한 직원  
> 목적: 회사의 **개발 프로세스, 협업 방식, 코드 품질 기준, 배포·운영·보안 원칙**을 이해하고  
> 실제 프로젝트에 바로 투입될 수 있도록 돕는 교육자료

---

## 0. 개발팀 공통 안내

### 0.1 이 문서의 목적

- 개발팀에서 일하는 사람이 반드시 알아야 할 **공통 기본기**를 정리한다.
- “어떤 언어/프레임워크를 쓰더라도” 공통적으로 적용되는 개발팀의 일하는 방식을 설명한다.
- 각 섹션은 다음 구조로 구성한다.
  - 업무 목적
  - 담당 범위
  - 단계별 프로세스
  - 사용하는 도구·시스템
  - 실무 시 유의사항
  - 체크리스트

---

### 0.2 개발팀의 핵심 역할

개발팀은 한 줄로 말하면 **“회사 서비스·시스템을 설계·구현·운영하는 부서”**다.

- **요구사항을 기술로 풀어내기**
  - 추상적인 아이디어/요구사항을
  - 설계, API, 데이터 구조, 화면, 로직으로 구체화
- **안정적인 서비스 제공**
  - 버그를 최소화하고
  - 장애가 나도 빨리 복구할 수 있는 구조 만들기
- **지속 가능한 코드베이스 유지**
  - 읽기 쉽고, 테스트하기 쉬운 코드 작성
  - 새 기능이 추가되어도 전체 품질이 유지되게 관리
- **보안·성능·확장성 고려**
  - 처음부터 보안/성능/확장성 기준을 넣고 개발
- **타 부서와의 기술 브릿지 역할**
  - 기획/디자인/운영/영업/고객사와 소통하며
  - 기술 제약·가능 범위를 설명하고 합리적인 대안을 제시

## DV-1. 개발 프로세스 & 이슈 기반 업무 흐름

### 1.1 교육 개요

- **교육 대상**
  - 모든 개발자(백엔드, 프론트엔드, 풀스택 등)
- **교육 목적**
  - 개발팀이 일하는 기본 흐름인  
    **“요구사항 → 이슈 등록 → 설계 → 구현 → 코드리뷰 → 테스트 → 배포”** 과정을 이해한다.
- **학습 후 기대 결과**
  - “개발팀이 어떤 단위로 일을 쪼개서 관리하는지(이슈/티켓 단위)” 설명할 수 있다.
  - 기능 추가·버그 수정 요청이 왔을 때, 어떻게 처리해야 하는지 전체 흐름을 말할 수 있다.

### 1.2 개발 업무 단위: 이슈/티켓

- 업무는 보통 다음 단위로 관리한다.
  - 기능 추가(Feature)
  - 버그 수정(Bug)
  - 개선/리팩터링(Improvement/Refactor)
  - 기술 부채 청산(Tech Debt)
  - 인프라/배포/모니터링 작업(Infra/DevOps Task)
- 각 이슈에는 최소한 다음 정보가 필요하다.
  - 제목
  - 배경/목적
  - 상세 요구사항 또는 재현 절차
  - 완료 기준(acceptance criteria)
  - 우선순위, 예상 난이도
  - 담당자, 예상 마감일

### 1.3 일반적인 개발 프로세스 흐름

1) **요구사항 접수**
   - 출처: 기획팀, 운영팀, 고객사, 내부 개발자 제안 등
   - 내용: 어떤 문제를 해결하고 싶은지, 목표는 무엇인지

2) **요구사항 정리 및 이슈 등록**
   - 개발에 적합한 형태로 정리
   - 이슈 트래킹 시스템에 등록(Jira, GitHub Issues 등)
   - 큰 덩어리는 여러 개의 작은 이슈로 나누어 관리

3) **우선순위 및 스프린트(또는 일정) 계획**
   - 어떤 이슈를 먼저 할지 결정
   - 스프린트(1~2주) 단위 또는 마일스톤 기준으로 계획

4) **설계(디자인)**
   - 데이터 구조/DB 설계
   - API 설계
   - 화면/UX 구조(프론트와 협업)
   - 기존 코드/구조와의 연결 검토

5) **구현(코딩)**
   - 코드 작성
   - 단위 테스트 작성
   - 기존 코드와 충돌 없는지 확인

6) **코드리뷰 & 품질 검토**
   - PR(MR) 작성
   - 동료 개발자의 코드 리뷰
   - 리뷰 의견 반영 후 머지

7) **테스트 & 배포**
   - 테스트 환경에 배포
   - 기본 기능·회귀 테스트 수행
   - 운영 환경에 릴리즈
   - 모니터링으로 이상 여부 확인

---

### 1.4 사용하는 도구·시스템 예시

- 이슈 트래킹 도구: Jira, GitHub Issues, GitLab Issues 등
- 형상관리: Git (GitHub, GitLab, Bitbucket 등)
- CI/CD: GitHub Actions, GitLab CI, Jenkins 등
- 협업 도구: Slack, Teams, Notion, Confluence 등

---

### 1.5 DV-1 업무 체크리스트

- [ ] 모든 개발 업무가 이슈/티켓 단위로 관리되고 있는가?  
- [ ] 이슈마다 “배경·내용·완료 기준”이 명확하게 적혀 있는가?  
- [ ] 기능 구현 전에 최소한의 설계/구조 논의를 하고 있는가?  
- [ ] 코드리뷰와 테스트를 거치지 않고 바로 운영에 반영되는 일이 없는가?

## DV-2. 요구사항 분석 & 설계 기본

### 2.1 교육 개요

- **교육 대상**
  - 기능 설계·API 설계·DB 설계를 수행하는 개발자
- **교육 목적**
  - “그냥 대충 만들어”가 아니라, **요구사항을 정확히 이해하고 설계로 녹이는 방법**을 배운다.
- **학습 후 기대 결과**
  - 요구사항을 보고 데이터/도메인/흐름 관점의 질문을 할 수 있다.
  - 간단한 기능이라도 설계 문서(또는 PR 설명) 수준으로 구조를 정리할 수 있다.

### 2.2 요구사항 분석 시 체크해야 할 것

- **문제 정의**
  - “이 기능은 어떤 문제를 해결하기 위한 것인가?”
- **사용자 관점 흐름**
  - 누가(Who), 언제(When), 무엇을(What), 왜(Why), 어떻게(How) 사용하는가?
- **예외 케이스**
  - 정상 흐름뿐만 아니라, 실패/에러/엣지 케이스까지 고려
- **연관 시스템·API**
  - 기존 기능과 충돌하거나 중복되는 건 없는가?
  - 다른 서비스, 외부 API와의 연동은?

### 2.3 설계 관점 세 가지

1) **도메인/데이터 관점**
   - 어떤 엔티티가 있는가? (예: User, Document, Order 등)
   - 엔티티 간 관계는? (1:N, N:M, 종속/속성 등)
   - DB 테이블/컬렉션 구조는? (키, 인덱스, 제약조건 등)

2) **API/서비스 관점**
   - 어떤 API가 필요하고, URL/메서드/파라미터/응답 구조는?
   - 인증/인가 규칙은?
   - 에러 코드와 에러 응답 형식은?

3) **플로우/시퀀스 관점**
   - 클라이언트 → 서버 → DB → 외부 시스템 순서
   - 요청이 들어와서 응답이 나가기까지 어떤 단계들을 거치는지

### 2.4 설계 산출물 예시

- 간단한 기능:
  - 이슈 티켓에 설계 노트로 정리
  - PR 설명에 “설계 요약” 문단 추가
- 복잡한 기능:
  - 별도의 설계 문서(Markdown/PDF 등)
  - 다이어그램(시퀀스 다이어그램, ERD 등)

### 2.5 설계 시 유의사항

- **확장성**
  - “이번 기능만 겨우 돌아가도록”이 아니라,  
    같은 패턴의 기능이 추가될 때 구조가 유지될 수 있도록 설계
- **일관성**
  - 기존 API/데이터 구조/코딩 스타일과 최대한 맞추기
- **보안·권한**
  - 이 API/기능을 누가 써도 되는지, 어떤 데이터까지 보여줘야 하는지

### 2.6 DV-2 업무 체크리스트

- [ ] 기능을 구현하기 전에, “무엇을/왜/누가/언제/어떻게”를 말로 설명할 수 있는가?  
- [ ] 데이터 구조와 API 구조가 요구사항과 일관되게 설계되었는가?  
- [ ] 정상 흐름뿐 아니라 실패/예외 케이스도 설계에 포함되어 있는가?  
- [ ] 기존 시스템과의 중복·충돌 여부를 검토했는가?

## DV-3. 코드 작성 규칙 & Git 기반 협업

### 3.1 교육 개요

- **교육 대상**
  - 모든 개발자
- **교육 목적**
  - **“나 혼자만 아는 코드”가 아닌 “팀이 함께 유지보수할 수 있는 코드”**를 작성하는 원칙을 익힌다.
  - Git 기반 브랜치 전략과 PR 중심 협업 방식을 이해한다.
- **학습 후 기대 결과**
  - 공통 코딩 컨벤션을 지켜서 코드를 작성할 수 있다.
  - Git 브랜치/커밋/PR 흐름을 설명하고, 실무에 적용할 수 있다.

### 3.2 코드 작성 기본 원칙

- **가독성 우선**
  - 변수/함수 이름은 “무엇을 하는지” 드러나게 짓기
  - 한 함수에 너무 많은 일을 몰아넣지 않기
- **일관성**
  - 팀에서 정한 코드 스타일/포맷(들여쓰기, 이름 규칙 등)을 따르기
  - 언어별 린터/포매터 사용(ESLint, Prettier, Black, isort 등)
- **주석 사용**
  - “왜 이렇게 했는지” 설명이 필요한 부분에만 주석
  - “코드만 봐도 아는 것”을 주석으로 중복하지 않기
- **에러 처리**
  - 예외 상황을 무시하거나 빈 catch 블록 두지 않기
  - 사용자/로그에 어떤 메시지를 남길지 설계

### 3.3 Git 브랜치 전략 (예시)

- 기본 브랜치:
  - `main` 또는 `master`: 항상 배포 가능한 상태
  - `develop`: 통합 개발 브랜치(선택 사항)
- 기능 브랜치:
  - `feature/이슈번호-간단한설명`
- 버그 픽스:
  - `fix/이슈번호-간단한설명`
- 릴리즈 브랜치(선택):
  - `release/버전`

일반적인 흐름 예시:

1. 이슈 할당 받음  
2. `main` 또는 `develop`에서 새 브랜치 생성 (`feature/...`)  
3. 기능 구현 및 테스트  
4. 원격에 브랜치 푸시  
5. PR 생성, 코드리뷰 요청  
6. 리뷰 반영 후 머지  
7. 머지된 코드가 배포 파이프라인을 통해 운영에 반영

### 3.4 커밋 메시지 작성 원칙

- 한 커밋에는 **논리적으로 관련된 변경만** 묶기
- 메시지는 **명령형 현재형**으로 짧고 명확하게
  - 예: `Add user detail API`, `Fix login session timeout`, `Refactor document parser`

커밋 메시지에 자주 포함되는 정보:

- 이슈 번호(있다면): `[#123] Add ...`
- 변경 타입: `feat:`, `fix:`, `refactor:`, `docs:`, `test:` 등(Conventional Commits)

### 3.5 PR(코드리뷰) 작성 원칙

PR에는 최소한 다음 내용 포함:

- 기능/변경 내용 요약
- 변경 이유/배경
- 주요 변경 파일/로직 설명
- 테스트 내용(어떤 케이스를 어떻게 테스트했는지)

코드리뷰 시 체크 포인트:

- 요구사항을 정확히 만족하는가?
- 로직이 이해하기 쉬운가? 복잡한 부분은 분리 가능한가?
- 에러/예외 시 동작은 적절한가?
- 보안상 문제는 없는가? (권한 체크, 입력 검증 등)
- 성능 상 심각한 이슈는 없는가? (N+1, 불필요한 반복 등)

### 3.6 DV-3 업무 체크리스트

- [ ] 팀에서 합의한 코딩 컨벤션과 포맷터를 적용했는가?  
- [ ] 한 PR 안에 너무 많은 종류의 변경을 섞지 않았는가?  
- [ ] 커밋 메시지와 PR 설명에 “왜/무엇을”이 드러나는가?  
- [ ] 코드리뷰를 통한 피드백을 열린 마음으로 수용하고 있는가?

## DV-4. 테스트·품질 관리 & 배포

### 4.1 교육 개요

- **교육 대상**
  - QA를 따로 두지 않거나, 개발자가 테스트까지 함께 담당하는 팀의 개발자
- **교육 목적**
  - “돌아가기만 하면 끝”이 아니라, 재발하지 않는 안정적인 코드를 만들기 위한  
    **테스트·품질 관리 기본 원칙**을 익힌다.
- **학습 후 기대 결과**
  - 기능 단위 테스트/간단한 통합 테스트를 작성할 수 있다.
  - 배포 전/후에 필수로 확인해야 할 체크리스트를 이해한다.

### 4.2 테스트의 종류(간단 분류)

- **단위 테스트(Unit Test)**
  - 함수/메서드 단위로 로직 검증
- **통합 테스트(Integration Test)**
  - 여러 모듈/컴포넌트가 함께 동작하는지 검증
- **API 테스트**
  - REST/GraphQL 등의 엔드포인트가 요구사항대로 동작하는지 검증
- **E2E 테스트(필요시)**
  - 실제 화면/사용자 행위 기준으로 전체 흐름 검증

### 4.3 개발자가 최소한 해야 할 테스트

- 새 기능 개발 시:
  - 대표적인 정상 케이스
  - 잘 나올 것 같은 에러 케이스 1~2개
- 버그 수정 시:
  - 버그 재현 케이스 기반 테스트
  - 같은 유형의 문제가 다시 발생하지 않도록 단위 테스트 추가

### 4.4 테스트·품질 관리 프로세스

1) **테스트 가능하게 코드 작성**
   - 너무 긴 함수/거대 클래스 → 테스트하기 어렵다 → 적당히 나누기
2) **PR 생성 전 로컬 테스트**
   - 최소한의 단위 테스트/기본 기능 수동 테스트
3) **CI(자동 테스트) 활용**
   - PR 생성 시 자동 테스트 실행
   - 실패 시 수정 후 재실행
4) **테스트 환경 배포 후 수동 점검**
   - 핵심 플로우(로그인, 주요 기능, 결제/저장 등)는 직접 눌러보며 검증
5) **운영 배포 전 최종 확인**
   - 변경 범위 점검
   - 주요 로그/알림 상태 확인

### 4.5 배포 기본 원칙

- **작게·자주 배포**
  - 한 번에 많은 변경을 모으지 않기
  - 작은 단위로 자주 배포하면, 문제가 생겨도 원인 찾기 쉬움
- **롤백 전략**
  - 문제가 생겼을 때 빠르게 이전 버전으로 되돌릴 수 있어야 함
- **배포 시간대**
  - 사용량이 상대적으로 적은 시간대 선택(내부 정책에 따름)
- **배포 후 모니터링**
  - 로그, 에러율, 응답 시간, 주요 지표 확인

### 4.6 DV-4 업무 체크리스트

- [ ] 새 기능/버그 수정 시, 최소한의 단위 테스트 또는 수동 테스트를 정의했는가?  
- [ ] PR 생성 전 로컬에서 테스트를 실행해봤는가?  
- [ ] CI에서 테스트가 모두 통과했는가?  
- [ ] 배포 후 주요 기능/지표를 모니터링하고 이상 여부를 확인했는가?

## DV-5. 운영·장애 대응 & 관측성(Logging/Monitoring)

### 5.1 교육 개요

- **교육 대상**
  - 운영 환경 장애 대응에 참여하는 모든 개발자
- **교육 목적**
  - 서비스 운영 중 발생하는 문제(에러, 장애, 성능 저하)를 탐지·분석·해결하는  
    기본 원칙과 절차를 이해한다.
- **학습 후 기대 결과**
  - 로그/모니터링 대시보드를 보고 현재 상태를 파악할 수 있다.
  - 장애 시 “어디부터 어떻게 확인해야 하는지” 순서를 말할 수 있다.

### 5.2 관측성(Observability) 구성 요소

- **로그(Log)**
  - 서비스 내부에서 발생하는 이벤트 기록
  - 에러/경고/정보 로그 레벨 구분
- **메트릭(Metrics)**
  - 요청 수, 에러율, 응답 시간, CPU/메모리 사용량 등 숫자 지표
- **트레이싱(Tracing, 선택)**
  - 하나의 요청이 여러 서비스/모듈을 통과하는 전체 경로 추적

### 5.3 로그 작성 기본 원칙

- **의미 있는 위치에 로그 남기기**
  - 중요한 비즈니스 이벤트(가입, 결제, 업로드, 승인 등)
  - 에러/예외 처리 지점
- **PII·민감정보 주의**
  - 로그에 주민번호, 계좌번호, 상세 개인정보 등은 남기지 않기
  - 필요 최소한의 식별자(예: user_id, document_id)만 기록
- **구조화된 로그**
  - 단순 문자열보다 key-value 형태(JSON 등) 사용하면 분석이 쉬움

### 5.4 장애 대응 기본 흐름

1) **탐지(Detection)**
   - 모니터링 알림
     - 에러율 증가, 응답 시간 급증, 특정 API 실패율 증가
   - 내부 사용자/직원 보고
2) **초기 대응**
   - 영향 범위 파악
     - 어느 기능/사용자에게 영향?
   - 심각도 판단
     - 전체 서비스 중단인지, 일부 기능 장애인지
3) **원인 조사**
   - 최근 배포/변경 사항 확인
   - 로그/메트릭 확인
   - 재현 가능한지 테스트 환경에서 확인
4) **임시 조치·완전한 조치**
   - 빠른 복구를 위한 임시 조치(롤백, 기능 비활성화 등)
   - 근본 원인 수정(코드 수정, 설정 변경, 인프라 조정 등)
5) **사후 분석(Postmortem)**
   - 장애 원인, 복구 과정, 재발 방지 대책 정리
   - 문서화 후 팀/관련 부서 공유

### 5.5 DV-5 업무 체크리스트

- [ ] 에러/이상 상황을 알 수 있는 로그·메트릭이 준비되어 있는가?  
- [ ] 장애 발생 시 확인해야 할 “체크 순서”를 팀 내에서 합의해두었는가?  
- [ ] 근본 원인과 재발 방지 방법을 문서로 남기고 공유하고 있는가?  
- [ ] 로그에 개인정보·민감정보를 남기지 않고 있는가?

## DV-6. 개발 보안·개인정보·규정 준수 기본

### 6.1 교육 개요

- **교육 대상**
  - 전 개발자(백엔드, 프론트엔드, AI, 데이터, DevOps 포함)
- **교육 목적**
  - 기능을 만드는 것뿐 아니라, **보안·개인정보 보호·내부 규정**을 지키는 개발 방법을 익힌다.
- **학습 후 기대 결과**
  - 기본적인 보안 원칙(입력 검증, 인증/인가, 암호화 등)을 설명할 수 있다.
  - 코드와 로그에서 개인정보를 어떻게 다뤄야 하는지 알고 있다.

### 6.2 인증(Authentiction) & 인가(Authorization)

- **인증**
  - “누구인지 확인하는 과정”
  - 예: ID/비밀번호, SSO, 토큰 기반 인증 등
- **인가**
  - “이 사용자가 무엇을 할 수 있는지 결정하는 과정”
  - 예: 롤(Role) 기반 권한, 리소스별 접근 권한 체크

개발 시 체크포인트:

- 보호해야 하는 API/페이지에 인증이 빠진 곳은 없는가?
- 민감한 데이터(개인정보, 내부 문서 등)에 접근 권한 체크가 되어 있는가?

### 6.3 입력 검증 & 취약점 방지

- **입력 검증**
  - 모든 외부 입력(요청 파라미터, 바디, 파일 등)은 검증이 필요
  - 길이 제한, 타입 체크, 허용된 값 목록 등
- **대표적인 취약점 예시**
  - SQL Injection: 쿼리에 직접 문자열 붙이지 않기, Prepared Statement/ORM 사용
  - XSS: 출력 시 HTML 이스케이프
  - CSRF: CSRF 토큰 활용(웹폼, 상태 변경 요청 등)

### 6.4 데이터·로그에서의 개인정보 처리

- **저장 시**
  - 꼭 필요한 정보만 저장
  - 암호화가 필요한 데이터(비밀번호, 일부 식별자)는 적절한 알고리즘 사용
- **전송 시**
  - HTTPS 사용(평문 전송 금지)
- **로그 시**
  - 주민번호, 계좌번호, 상세 주소 등은 로그에 남기지 않기
  - 필요 시 마스킹 처리(예: 010-****-1234)

### 6.5 외부 서비스·오픈소스 사용

- 라이선스 확인
  - 오픈소스 라이선스를 준수해야 함(복제, 수정, 배포 조건 등)
- 외부 API 호출 시
  - 토큰/키를 코드에 하드코딩하지 않기(환경변수/비밀관리 사용)
  - 요청/응답에 개인정보가 포함되는지 확인

### 6.6 DV-6 업무 체크리스트

- [ ] 모든 중요 API에 대해 인증/인가가 올바르게 적용되어 있는가?  
- [ ] 외부 입력값을 적절히 검증하고, 오류/예외를 안전하게 처리하고 있는가?  
- [ ] 로그에 불필요한 개인정보·민감정보를 남기지 않고 있는가?  
- [ ] 오픈소스/외부 API 사용 시 라이선스·보안·키 관리 규정을 지키고 있는가?

## 부록 A. 개발팀 공통 용어 정리

- **SDLC(Software Development Life Cycle)**  
  요구사항 분석 → 설계 → 구현 → 테스트 → 배포 → 운영/유지보수의 전체 개발 생명주기.

- **Refactoring(리팩터링)**  
  코드의 동작은 그대로 유지하면서, 구조·가독성·유지보수성을 개선하는 작업.

- **Tech Debt(기술 부채)**  
  빠른 개발을 위해 잠시 미뤄둔 구조 개선/리팩터링/테스트 등의 “빚”으로,  
  나중에 반드시 갚아야 하는 기술적 문제들.

- **CI/CD(Continuous Integration / Continuous Delivery/Deployment)**  
  코드를 자주 통합하고 자동으로 빌드·테스트·배포하는 파이프라인.

- **Observability(관측성)**  
  로그, 메트릭, 트레이싱 등을 통해 시스템 내부 상태를 외부에서 잘 관찰할 수 있는 능력.
